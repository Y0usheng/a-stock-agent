# 订阅请求完成后仍被报超时的原因与修正

2026-10-30的30秒最小诊断在截止前已经观察到 `thread.started`、`turn.started`、`item.completed` 和 `turn.completed`，但旧适配器仍等待CLI进程退出，随后终止进程并报告超时。客户端收尾卡住会因此遮蔽已经完成的模型响应。这是已经复现的程序问题，不能把所有等待都解释为模型推理慢。

适配器现在读取完整的JSONL行，发现终止事件后先校验最终JSON、完整用量、单回合约束、错误事件和禁止工具活动，再清理该请求的子进程并返回响应。不再要求进程自行退出才承认推理完成。主动清理可能使进程退出码非零，因此诊断同时记录 `validated_terminal_result`，将经过校验的响应与进程退出码分开审计。仅有答案文字、缺少终止事件或有效用量、含不可恢复错误或工具活动的输出仍不能被采用。

官方[非交互模式文档](https://learn.chatgpt.com/docs/non-interactive-mode)说明JSONL中的回合完成事件包含用量。程序据此判断响应完整性；这项检查不替代证据、投资论证、独立风控和人工交易确认。

验证包括：本地子进程发出完整响应后持续运行，适配器仍及时返回并清理；缺少终止用量的消息继续超时；异常用量和错误事件仍被拒绝。275项回归通过。

修正后的真实最小请求使用原模型 `gpt-6.1-sol`，于2026-10-30 01:13:23开始，约33.6秒后返回有效JSON；输入5,883、输出15，共5,898 tokens，完整用量已记录。没有选股或交易，也没有提高原有超时和预算。

先前还观察到匿名HTTPS探测中的TLS失败，但它不能代替官方客户端的实际模型通路测试。之前主要归因代理的判断不充分：目前确认存在上述适配器缺陷，网络错误可能同时存在。旧超时请求的原始临时输出已经清理，无法证明每次历史超时都由同一原因造成，也不能补造其精确用量。真实投资流程仍需独立完成端到端验收。

后续实际公司研究观察到断流重连、最终agent消息与turn.completed，但旧解析器把中间连接提示一并拒绝，已知完成用量为13,087 tokens。修复只识别严格格式的`Reconnecting... n/m`提示（总数及重连上限不超过5）；含明确认证、额度、权限或审批错误、其他error、turn.failed、任何工具活动、缺失最终有效JSON/用量、完成后再出现重连或多个完成回合仍拒绝。没有延长调用限时、增加重试或更换模型。传输恢复次数记录在本机回执；原生CLI较早未完成连接尝试的服务端用量不可得，不能把终止事件用量解释为完整HTTP尝试成本。

晚间基本面调用再次出现两个error事件及完整完成用量7,210 tokens，因未匹配有限重连规则而拒用。旧回执没有保留具体事件结构，无法事后确定其内容；同一冻结输入的单步复测随后在24.9秒内通过，未复现错误。现在本机回执另保留拒用原因、计数器格式、固定词汇、已知字段是否存在和显式重试布尔值，不保留任意错误正文、URL、账号或线程身份。该诊断改动不放宽接收规则，便于下次直接定位间歇性事件差异。
